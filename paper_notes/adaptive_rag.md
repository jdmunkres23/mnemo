## 1패스 — 전체 구조 파악

> Abstract + 섹션 제목 + Conclusion + 그림/표 제목만 훑은 후 작성

**이 논문이 다루는 문제:** 서로 다른 복잡도를 가진 질문에 일괄적으로 복잡한 처리를 하는 문제
수정 : No-retrieval·Single-hop·Multi-hop 각각 잘하는 질문 유형이 다른데,
기존 연구는 하나의 전략을 모든 질문에 고정 적용해 비효율·오답 발생.

**기존 방법의 한계:** 가벼운 질문에도 복잡한 프로세스를 거쳐서 대답을 만들어 낸다.
추가 : No-retrieval: 단순 질문엔 빠르지만 복잡한 질문엔 부족
Single-hop: 중간 수준엔 좋지만 단순 질문에 낭비
Multi-hop: 복잡한 질문엔 강하지만 단순 질문에 오히려 오답 유발


**한 줄 요약 (초안):** 질문의 수준에 맞게 복잡한 정도에 따라서 처리하는 프로세스인 Adaptive-RAG를 만들었다.
수정 : 소형 분류기가 질문 복잡도를 판단해
No-retrieval / Single-hop / Multi-hop 중 적합한 전략을 동적으로 선택하는 Adaptive-RAG.

## 2패스 — 흐름과 핵심 이해

> Introduction / Method / Experiments / Results 읽은 후 작성

**핵심 아이디어:** 질문의 복잡도에 따라 어떤 전략을 사용할지 분류할 분류기를 중간에 두자.
추가 : 분류기 학습 라벨이 원래 없으므로 2단계로 자동 생성함.
  1) 같은 질문에 no-retrieval → single-hop → multi-hop 순서로 실제로 시도해서, 가장 단순한 전략이 정답을 맞히면 그 복잡도로 라벨링
  2) 1)로도 라벨이 안 정해진 질문은 출처 데이터셋으로 라벨링 (single-hop 데이터셋 출신 → B, multi-hop 데이터셋 출신 → C)

**실험 및 결과:**
데이터셋 — single-hop: SQuAD v1.1, Natural Questions, TriviaQA / multi-hop: MuSiQue, HotpotQA, 2WikiMultiHopQA
지표 — 정확도(F1/EM/Accuracy) + 효율성(검색-생성 스텝 수, 쿼리당 시간)

눈에 띈 결과:
FLAN-T5-XL(3B) 기준 Adaptive-RAG F1 46.94 (single-hop 고정 44.31보다 높음), 평균 스텝 1.084 (multi-hop 고정 4.69 대비) → 시간 약 60% 절감.
Oracle 분류기 사용 시 F1 56.28 — 실제 분류기(46.94)와 약 10점 차이.

**한계 및 아직 못 푼 것:** 분류기가 완벽하게 좋은 성능을 내기 위해서 추가적인 연구가 필요함.
추가 : 위 Oracle-실제 격차(56.28 vs 46.94)가 그 증거. 라벨 자체가 모델 예측 + 데이터셋 편향에 의존하는 자동 생성 라벨이라 골드 라벨이 아님 → 분류기 품질이 라벨링에 쓰인 하위 QA 모델 성능에 종속되는 순환 구조.

**다른 논문과의 연결:**
RAG(1회 검색) → Self-RAG(검색 필요 여부 스스로 판단) → FLARE/IRCoT(생성 중 불확실하면 재검색) 흐름의 연장선. 이 논문은 "검색 여부/횟수를 질문 복잡도로 미리 분류"한다는 점에서 위 흐름과 달리 생성 전에 한 번에 전략을 결정.

**내 프로젝트에 어떻게 쓸 수 있을까:** 개인 대화에서는 분류기를 학습시킬 수 없으므로 가벼운 모델로 분류기를 두고 실험을 진행한다.대신 프롬프트로 조절한다.
- 문제는 어떻게 성능을 평가할 것인지이다.
추가 : Oracle vs 실제 분류기 격차를 측정한 방식 그대로, `evaluator.py`에서 라우팅 분류 정확도(simple/analytical/retrieval 골드 라벨 대비)를 RAG 답변 품질과 분리해서 측정하면 됨.

## 3패스 — 구현 목표로 깊이 읽기

> 수식·알고리즘을 따라가며 재현 가능한 수준으로 읽은 후 작성

**방법론 이해:** LLM이 답을 하기 전에 분류기를 통해 얼마나 복잡한 작업이 필요한지 분류 후 LLM에게 넘긴다.(분류기 학습 직접 구현하지는 않을 것이므로 간단한게 작성)

이해가 안 된 부분:

**의문점 / 납득 안 되는 부분:** 애매한 부분들을 분류기가 완전히 커버하기가 어려울 텐데 그냥 복잡한 단계로 넘기면 오히려 할루시네이션이 발생할 수도 있을 것 같다는 생각이들었음. 완벽한 분류기가 존재하기 어려울 것 같은데 이 오차와 효율성 사이의 트레이드 오프가 있을 것으로 생각됨.

**한 줄 요약 (최종):** 중간에 분류기를 두어서 효율적으로 LLM을 사용하자.
